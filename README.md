# 🤖 Study Assistant

> Ассистент, который читает учебные материалы и отвечает на вопросы по ним.
> Курсовой проект специальности 09.02.13 «Интеграция решений с применением технологий ИИ».

---

## 📖 Что это за программа

Вы собираете инструмент, который решает настоящую задачу: у вас есть конспекты, и вы хотите задавать по ним вопросы обычным языком, а не искать глазами по файлам.

К концу курса программа умеет:

- читать папку с конспектами и разбирать их на фрагменты;
- находить фрагменты, подходящие к вопросу;
- отправлять найденное языковой модели и получать ответ;
- работать через Telegram-бота;
- и — самое важное — **показывать цифрами, на сколько вопросов она отвечает верно**.

Последний пункт отличает рабочее решение от демонстрации. «Запустить нейросеть» умеют все; доказать, что она не врёт, — почти никто.

## 🧱 Как устроен проект

```
study-assistant/
├── main.py                  точка входа
├── study_assistant/         пакет с логикой — растёт весь курс
│   ├── material.py          учебный материал
│   ├── catalog.py           чтение и сохранение каталога
│   └── source.py            откуда берутся материалы
├── materials/               ваши конспекты (пока учебные примеры)
├── stages/                  задания по этапам, у каждого свой README
├── tests/                   автотесты по этапам
├── pyproject.toml           зависимости и настройки
└── justfile                 короткие команды (необязательно)
```

Ключевая идея: **код не выбрасывается и не копируется между этапами**. Пакет `study_assistant` один, он просто обрастает новыми модулями. Функция, написанная на первом этапе, доживает до защиты проекта.

## 🚀 Начало работы

### 1. Форкните репозиторий

Кнопка **Fork** вверху страницы. Этот форк — ваш проект до конца курса, форкать заново на каждом этапе не нужно.

### 2. Склонируйте и подготовьте окружение

```bash
git clone https://github.com/ВАШ_ЛОГИН/study-assistant.git
cd study-assistant
uv sync
```

Команда `uv sync` установит Python 3.14 и инструменты разработки: `pytest` для тестов и `ruff` для проверки стиля.

### 2а. Необязательно: сокращения команд через `just`

В проекте есть `justfile` — набор коротких команд вроде `just test` вместо
`uv run pytest`. Это удобно, но **не обязательно**: все команды в этом README
написаны полностью, и `just` можно не устанавливать.

```bash
uv tool install rust-just    # установка, работает на macOS, Linux и Windows
just                         # список доступных команд
```

> 💡 `just` печатает команду, которую выполняет. Так вы видите настоящие
> команды `uv` и постепенно запоминаете их — а на экзамене или на работе
> `just` может и не оказаться.

### 3. Посмотрите, что уже работает

```bash
uv run pytest
```

Увидите список тестов. Часть провалится, часть будет пропущена — это нормально: код ещё не написан. Тесты и есть ваше задание в исполняемом виде.

### 4. Откройте задание текущего этапа

Ссылка в таблице выше. Там написано, что именно нужно сделать и почему.

## 🧪 Как проверять себя

Тесты — основной способ понять, готова работа или нет.

```bash
uv run pytest                  # все тесты
uv run pytest -m stage1        # только текущий этап
uv run pytest -x               # остановиться на первой ошибке
uv run pytest -m stage1 -x     # разбирать текущий этап по одной ошибке
```

Если установили `just`, то же самое короче:

| Короткая команда | Что выполняет                                        |
|---|------------------------------------------------------|
| `just` | список всех команд                                   |
| `just test` | `uv run pytest -v`                                   |
| `just stage 1` | `uv run pytest -m stage1 -x`                         |
| `just contract` | `uv run pytest -m contract`                          |
| `just lint` | `uv run ruff check .`                                |
| `just fix` | `uv run ruff check --fix .` и `uv run ruff format .` |
| `just check` | стиль и тесты — то же, что проверит преподаватель    |
| `just run` | `uv run main.py`                                     |
| `just clean` | удалить кеши и `catalog.json`                        |

> 💡 **Совет для начала работы.** Запускайте с флагом `-x`. Тогда pytest покажет одну ошибку вместо двадцати, вы её исправите, запустите снова — и так по очереди. Двадцать красных строк сразу никому не помогают.

### Что означают результаты

| Символ | Значение |
|---|---|
| `.` | тест прошёл |
| `F` | тест провалился — ниже будет написано, что именно не так |
| `s` | тест пропущен: нужная функция пока не написана |

В конце прогона печатается итог: сколько пройдено, сколько пропущено, сколько не проходит.

### Проверка стиля

```bash
uv run ruff check .        # найти замечания
uv run ruff check --fix .  # исправить, что можно, автоматически
uv run ruff format .       # отформатировать код
```

Линтер находит не только пробелы: он ловит неиспользуемые импорты, опечатки в именах и изменяемые значения по умолчанию.

### Запуск программы

```bash
uv run main.py
```

## 🧭 Как читать тесты

Тесты — это описание того, чего от вас ждут, в виде кода. Читать их полезно: там нет двусмысленностей, которые бывают в текстовом задании.

Файлы в `tests/` делятся на два вида.

**`test_contract.py`** — поведение, неизменное на всех этапах. Отчёт программы выглядит определённым образом, и он не должен измениться, сколько бы вы ни переделывали внутреннее устройство. Этот файл живёт весь курс.

**`test_stage_NN_*.py`** — требования конкретного этапа: какие функции появились, что они возвращают.

> 💡 Тесты этапа иногда **перестают быть актуальными**, когда следующий этап меняет контракт функции. Например, на этапе 1 `read_material` возвращала словарь, а на этапе 2 — объект. Это нормальная инженерная ситуация: изменился контракт — изменились тесты. В задании этапа написано, что именно нужно поправить.
>
> А вот `test_contract.py` не меняется никогда. Если он покраснел — вы сломали поведение программы, а не улучшили её устройство.

## 🏁 Как сдавать этап

Каждый этап сдаётся отдельным Pull Request.

```bash
git switch -c stage-2-material      # ветка под этап
# ... работа ...
uv run pytest                         # проверить тесты
uv run ruff check .                   # проверить стиль
git add .
git commit -m "Этап 2: материал стал объектом класса Material"
git push origin stage-2-material
```

С `just` две проверки сводятся к одной команде — `just check`.

Затем откройте Pull Request из своей ветки в `main` **вашего форка** и пришлите ссылку преподавателю.

В описании PR укажите:

- результат `uv run pytest` (текст или скриншот);
- что оказалось самым трудным;
- если пользовались ИИ-ассистентом — что сделали с его помощью и что проверили вручную.

> ⚠️ **Не сливайте PR сами.** Преподаватель оставит комментарии — это code review, часть задания.

Подробные критерии оценивания — в README конкретного этапа.

## ❓ Если застряли

1. **Прочитайте докстринг функции** — там описано, что она должна вернуть.
2. **Посмотрите на `TODO` в теле** — они разбивают задачу на шаги.
3. **Прочитайте тест**, который не проходит. Он показывает конкретные значения, которых от вас ждут.
4. **Запустите с `-x`** и читайте только первую ошибку.
5. **Проверьте одну функцию отдельно.** Создайте файл `try.py` в корне:

   ```python
   from study_assistant.material import Material

   sample = Material("test.md", "Проверка", 2, 5, 40)
   print(repr(sample))
   print(sample.summary())
   ```

   Файл `try.py` в `.gitignore` — коммитить его не нужно.
